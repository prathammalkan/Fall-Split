# Fall Split — Security Notes

## Authentication

- All authentication is handled by **Supabase Auth** — no custom password storage.
- Passwords are hashed by Supabase (bcrypt-based). Fall Split never sees plaintext passwords.
- Sessions use **PKCE flow** (`flowType: 'pkce'`) to prevent authorization code interception.
- `autoRefreshToken: true` keeps sessions alive; `persistSession: true` uses `localStorage`.
- Magic links and OTP codes expire. They are single-use.

## Account Enumeration

- Auth error messages are deliberately vague ("Invalid credentials") to avoid revealing whether an email is registered.
- Username search returns only profiles, never email addresses.
- Invitation tokens are opaque random strings — they do not embed email or user ID.

## Row Level Security (RLS)

RLS is enforced at the **PostgreSQL level**, not the application layer. Even if the application code has a bug, the database will reject unauthorized queries.

Key policies:
- Users can only read their own profile or profiles of friends and group members.
- Only expense creators and involved parties can read expenses.
- Group expenses are only accessible to current group members.
- Removed group members lose access immediately.
- Settlements are only visible to the payer and recipient.

## API Keys

- Only the **anon key** (`VITE_SUPABASE_ANON_KEY`) is in the browser bundle. It is safe to expose.
- The **service-role key** must NEVER appear in any `VITE_` variable or client-side code.
- The anon key, combined with RLS, is the intended Supabase client-side security model.

## Invitation Tokens

- Tokens are generated with `gen_random_uuid()` or equivalent — cryptographically random.
- Tokens have configurable expiry and `max_uses`.
- Tokens can be revoked (`revoked_at`) server-side.
- QR codes contain only the invite URL with the opaque token — no private user data.
- The `accept_invitation` RPC runs `FOR UPDATE` to prevent race conditions on `use_count`.

## Financial Data

- All monetary values are stored as **integer paise** — no floating-point rounding errors.
- Expense allocations are validated to reconcile exactly to the total before being written.
- Balances are derived from immutable ledger records, not cached fields that can drift.
- Settlements require **both-party confirmation** before affecting balances.

## UPI Disclaimer

UPI payment links generated by Fall Split:
- Are convenience links only — they do NOT prove payment occurred.
- Fall Split does not verify, intercept, or store UPI transactions.
- Settlement confirmation requires the recipient to manually confirm receipt.

## CSV Export

- All CSV fields are escaped to prevent formula injection attacks (cells starting with `=`, `+`, `-`, `@` are prefixed with a tab character).

## Headers

The `vercel.json` sets these security headers on all responses:

| Header | Value |
|---|---|
| `X-Frame-Options` | `DENY` |
| `X-Content-Type-Options` | `nosniff` |
| `X-XSS-Protection` | `1; mode=block` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` |

## Reporting Issues

If you discover a security vulnerability, please report it privately by opening a GitHub issue marked **[SECURITY]** or emailing the maintainer directly. Do not disclose publicly until patched.
